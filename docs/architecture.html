deck.gl 参考场景架构

十二个自包含的 deck.gl 可视化场景，覆盖 GPU 聚合、动画轨迹、地理流、等值线、地块、标注与点场，全部离线运行、无底图依赖、无运行时网络请求。

12 个场景 纯前端渲染 确定性合成数据 浏览器端验证管线

1产品概述

deckgl-examples 是一组以 deck.gl 9.x 为核心的可视化参考场景集合。 它的定位是「可视化技术演示与回归测试样本库」——每个场景都独立解决一类地理/空间可视化问题， 同时共享一套统一的数据生成、渲染管线和验证机制。

项目的核心设计原则是离线第一：所有数据由确定性伪随机函数在浏览器端生成， 不依赖任何底图服务、瓦片服务或外部数据 API。这使得项目可以在完全断网的环境下运行， 也让自动化回归测试变得简单可靠。

◆

GPU 聚合渲染

HexagonLayer / GridLayer / ContourLayer 在 GPU 上完成数十万级数据的密度聚合与等值线提取。

◈

动画时间轴

TripsLayer 按时间戳驱动 2,400 条移动轨迹，配合静态路网层保留空间上下文。

⇌

网络流与弧线

PathLayer 曲线 + ArcLayer 大弧线两种方式表达 OD 流量，宽度/高度/颜色联合编码强度。

◇

无底图设计

全部场景透明背景渲染，不依赖 Mapbox/Google 底图，可直接叠加到任意宿主页面。

◫

透明 PNG 导出

export=1 模式输出纯透明背景画布，可直接用于文档、报告或设计稿素材。

✓

像素级验证

Playwright + pngjs 自动验证每个场景的不透明像素占比、彩色像素数量和透明背景覆盖率。

技术栈

2系统分层架构

整个项目采用经典的四层结构：数据层负责生成确定性合成数据， 渲染层以 deck.gl 图层为核心，交互层处理视图控制与动画循环， 验证层则在 CI/回归测试中保障渲染质量。

图 1 · 自顶向下的四层架构，每层职责单一，数据单向流动

各层职责详解

数据层是整个项目的基础。它不调用任何外部 API，而是通过一个基于 Math.sin 的伪随机函数 pseudo() 生成确定性数据。 这样做的好处是：每次加载同一个场景，看到的画面完全一致；不需要携带数据文件；也不会因网络波动导致测试不稳定。 数据层产出五种典型结构：点云（Point）、轨迹（Trip）、节点对（Flow）、多边形（Parcel）和分支（Branch）。

渲染层是项目的核心，完全构建在 deck.gl 9.x 之上。它使用了 deck.gl 的四个子包： @deck.gl/core 提供 Deck 实例和视图系统，@deck.gl/layers 提供基础图层（ScatterplotLayer / PathLayer / PolygonLayer / ArcLayer / TextLayer）， @deck.gl/aggregation-layers 提供 GPU 聚合图层（HexagonLayer / GridLayer / HeatmapLayer / ContourLayer）， @deck.gl/geo-layers 提供 TripsLayer 时间轨迹。场景之间的切换通过 URL 参数 ?scene= 完成。

交互层处理两种视图模式：OrbitView（轨道视图，用于 3D 场景如六边形柱和地块）和 OrthographicView（正交视图，用于 2D 平面场景）。 拖拽、缩放、旋转都由 deck.gl 内置控制器处理。Trips 场景额外维护一个 requestAnimationFrame 循环， 逐帧更新 currentTime 来驱动轨迹动画。

验证层是这个项目与普通 demo 最大的区别。它不只是「能跑就行」，而是通过 Playwright 驱动真实 Chrome 浏览器， 对每个场景执行一套完整的检查清单：页面加载后 __plotDemo.ready 标志为真、数据量与元数据正确、 鼠标拖拽能触发视图变化、控制台无错误、不发起任何外部请求、截图有足够彩色像素、透明导出有足够内容像素和足够透明背景。

设计要点：验证层拦截所有非本地请求，这是「离线第一」原则的强制执行手段。 如果未来某个场景误引入了外部瓦片或字体 CDN，测试会立即失败并指出请求 URL。

4主走查 · 场景渲染验证

选取「六边形密度场景的渲染验证」作为端到端走查用例，共分 5 步。 这是项目最典型的执行路径：从开发构建到浏览器渲染，再到像素级质量检查。

图 3 · 主走查五步流水线：从构建到像素校验的完整闭环

步骤 1：Vite 构建 构建

执行 npm run build，TypeScript 先做类型检查（tsc --noEmit），通过后 Vite 将 src/main.ts 打包成静态资源，输出到 dist/ 目录。整个过程是纯本地的，不需要任何网络连接。

步骤 2：启动预览服务 服务

验证脚本 scripts/validate.mjs 以子进程方式启动 vite preview，监听 41731 端口。脚本轮训 HTTP 直到服务就绪（最多 10 秒），确保后续浏览器访问不会失败。

步骤 3：Playwright 加载场景 加载

脚本启动系统 Chrome（headless 模式），为每个场景新建页面，访问 /?scene=hexagons。页面路由解析 URL 参数，生成 12 万个确定性点云数据，创建 HexagonLayer 并挂载到 Deck 实例。脚本等待 window.__plotDemo.ready === true，这是首帧渲染完成的信号。

步骤 4：交互与元数据验证 交互

脚本读取运行时元数据（itemCount、scene 名称）确认正确；模拟鼠标拖拽画布，检查视图状态变化次数 ≥ 1，证明控制器和事件管线工作正常；同时拦截所有外部请求——只要有一个非本地请求就记为失败。

步骤 5：像素级质量校验 校验

分别截取普通视图和 export=1 透明模式的 PNG。使用 pngjs 逐像素检查：普通截图不透明像素 ≥ 95% 且彩色像素 ≥ 3500 个（证明有真实内容）；透明导出透明像素 ≥ 10% 且内容像素 ≥ 2500 个（证明背景透明且图形存在）。全部通过后写入 out/ 目录。

为什么走查这个场景？Hexagons 场景综合了 GPU 聚合、3D 轨道视图、大数量级点云和透明导出，几乎覆盖了项目所有关键技术点。 如果这个场景能跑通且通过像素校验，其余十一个场景的核心路径也基本可靠。

5渲染管线详解

以一个典型的聚合场景为例，数据从生成到最终呈现在画布上，经过了哪些阶段？ 理解这条管线有助于排查「为什么画面是空的」「为什么聚合结果不对」等常见问题。

图 4 · GPU 聚合场景的渲染管线：数据从 CPU 进入 GPU 完成分箱与着色

管线各阶段说明

数据生成阶段完全在 CPU / JS 主线程完成。pseudo() 函数以索引和盐值为输入， 通过正弦函数的小数部分产生 0–1 之间的伪随机值。虽然不是密码学安全的随机数，但对于可视化演示来说完全够用， 关键是可复现——相同的索引永远产生相同的值。

Deck 实例阶段是 deck.gl 的入口。new Deck({...}) 接收视图配置、图层数组和回调函数。 deck.gl 内部会管理 WebGL 上下文、属性缓冲区和渲染循环。对于聚合类图层，数据会被上传到 GPU 作为纹理或顶点缓冲区。

GPU 聚合阶段是 HexagonLayer 和 GridLayer 的核心优势所在。 传统做法是在 CPU 上遍历所有点、计算每个点属于哪个网格单元、累加权重——对于十万级数据就开始吃力。 deck.gl 的聚合图层把这个过程搬到 GPU 上，利用并行计算能力在几毫秒内完成分箱（binning）， 因此 12 万个点的六边形聚合可以做到 60fps。

颜色与高程映射阶段将聚合后的标量值（每个六边形单元的权重和）映射为视觉属性。 颜色使用分位数尺度（quantile scale），确保每种颜色的六边形数量大致相等，避免因极值导致色阶失效。 高程则是线性映射，并通过 elevationScale 控制整体高度。

视图系统是并行于图层管线的另一条支路。OrbitView 提供 3D 轨道视角（支持旋转和俯仰）， OrthographicView 提供 2D 正交视角（没有透视变形，适合平面数据）。 视图状态的变化不会触发数据重新聚合，只会重新计算投影矩阵，因此交互非常流畅。

6目录与数据流

项目结构精简，核心代码集中在一个 main.ts 文件中。 这既是优点（简单、易读），也是有意识的设计决策——示例项目的代码应该让人一眼看懂，而不是藏在层层抽象后面。

图 5 · 从源码到构建产物再到浏览器运行时，最后回环到验证输出

关键文件说明

src/main.ts 是整个项目的核心，也是唯一的应用入口文件。它同时承担了数据生成、场景注册、Deck 初始化、图层配置、UI 渲染和动画循环的职责。 对于示例项目来说，单文件结构让读者可以从头到尾读完理解全貌，不需要在多个文件之间跳转。

catalog.json 是场景的元数据清单，记录每个场景的 ID、用途、视觉语系、复杂度级别和标签。 它既是文档索引，也是验证脚本的数据源——脚本遍历这个列表来决定要测试哪些场景。

scripts/validate.mjs 是验证管线的执行者。它使用 ES Module 语法（因此是 .mjs 后缀）， 通过 Playwright 驱动 Chrome 浏览器，用 pngjs 做像素分析。整个验证过程不依赖任何第三方测试框架。

out/ 目录存放每个场景的两套截图：带 UI 的普通截图和纯透明背景的导出图。 这些 PNG 文件既是测试通过的产物，也可以直接作为文档插图或设计素材使用。

7设计决策与取舍

每个架构选择都有其代价。以下是本项目中几个关键决策背后的考量， 理解这些权衡有助于判断项目是否适合你的使用场景，以及在什么情况下应该换一种做法。

决策 1：单文件架构 vs 模块化拆分

选择：所有场景代码放在一个 main.ts 中，没有拆分为多个场景模块。

理由：作为参考示例项目，可读性和可移植性优先。读者复制一个场景的代码时， 不需要从三四个文件里拼凑依赖。单文件也使得 Vite 构建产物更精简——不需要按需加载的额外复杂度。

代价：当场景数量增加到 20+ 或每个场景需要独立的复杂逻辑时，单文件会变得臃肿。 届时应该按场景拆分模块，用动态 import 做按需加载。

决策 2：纯前端合成数据 vs 内置数据文件

选择：所有数据通过伪随机函数即时生成，不携带任何 CSV / JSON 数据文件。

理由：零网络依赖、零数据体积、完全可复现。对于演示和回归测试来说， 数据的真实性不重要，重要的是数据结构的典型性和渲染结果的稳定性。

代价：不能展示真实数据的洞察价值。如果项目目标从「技术演示」转向「数据叙事」， 就需要替换为真实数据集，并考虑数据加载和增量更新策略。

决策 3：无底图设计 vs 集成底图

选择：所有场景使用透明背景，不集成 Mapbox / Google Maps / Carto 等底图服务。

理由：底图服务通常需要 API key、产生网络请求、增加验证复杂度。 无底图设计让示例更「干净」——你可以把它叠加到任何地图或页面上，也可以直接导出透明 PNG 用在设计稿中。

代价：缺少地理上下文，用户不容易对应到真实地理位置。 但 deck.gl 的图层本身支持经纬度坐标，未来需要时可以无缝接入 MapView + 底图。

决策 4：像素级验证 vs 快照对比

选择：使用像素统计阈值（不透明占比、彩色像素数、内容像素数）而非全图快照对比。

理由：全图快照对比对渲染环境极其敏感——不同 GPU、不同驱动版本、不同抗锯齿设置 都会产生像素级差异，导致大量假阳性失败。统计阈值方法更鲁棒，只验证「画面有内容、背景正确、不是空白」这些核心属性。

代价：不能检测细微的渲染回归（比如某个颜色值变了 5%）。 但对于示例项目来说，「能正常渲染」比「每个像素完全一致」更重要。

8扩展与演进方向

作为示例项目，它已经覆盖了 deck.gl 最常用的图层类型。但如果要进一步演化为更完整的可视化框架， 以下几个方向值得探索。

⇪

真实数据接入

接入 GeoJSON / CSV / Parquet 等真实数据集，支持本地文件拖拽加载或远程 API 拉取。

⊞

底图可选集成

将 Mapbox / MapLibre 作为可选底图，通过 URL 参数切换有底图 / 无底图模式。

⚙

图层参数面板

为每个场景增加交互式控制面板，实时调整半径、颜色、聚合方式等参数，便于学习调试。

⎘

场景模块化

将十二个场景拆分为独立模块，支持动态 import 和自定义场景注册机制。

⬜

WebGPU 迁移

关注 deck.gl 对 WebGPU 的支持进展，在合适时机验证 WebGPU 后端的性能与兼容性。

⧉

3D Tiles / 点云

引入 Tile3DLayer 和 PointCloudLayer，覆盖城市级三维模型和激光点云场景。
